## Индустрия разработки ПО сегодня

- GitHub — **100+ млн разработчиков**; большая часть ПО пишется **командами**, а не одиночками
- По опросам Stack Overflow, на написание кода уходит **меньше половины** рабочего времени: остальное — чтение чужого кода, ревью, отладка, согласования
- Тренды зрелых команд: **CI/CD-конвейеры, контейнеры, код-ревью, автотесты, мониторинг**
- ИИ-ассистенты ускоряют набор кода, но не отменяют процессов: ревью, тесты и релизная дисциплина остались

> Курс учит именно «второй половине» профессии — инженерной дисциплине

## Анализ и проектирование ПО

**Системный анализ** — исследование предметной области; результат — требования и модели AS-IS / TO-BE.

**Проектирование ПО** — создание моделей системы: архитектура, данные, интерфейсы, алгоритмы.

- Анализ отвечает на вопрос: **«ЧТО** делает система?»
- Проектирование — **«КАК** она будет это делать?»
- Третья деятельность — **конструирование**: код по моделям

> Результат — модели и документы, а не код

---

## Мой проект: ЧТО и КАК

**ЧТО** (системный анализ - задачи пользователя трекера личных финансов):
- **Учитывать** ежедневные доходы и расходы с распределением по индивидуальным категориям
- **Устанавливать** месячные лимиты бюджетов и получать предупреждения при их превышении
- **Формировать** аналитический отчет с графиками динамики накоплений за выбранный период

**КАК** (архитектурное проектирование - инженерные решения):
- **Хранение данных**: реляционная СУБД PostgreSQL (ACID-транзакции для денежных проводок)
- **Интерфейс**: адаптивный веб-приложение (React, TypeScript, Tailwind CSS)
- **Ключевые сущности**: `User`, `Account`, `Category`, `Transaction`, `BudgetLimit`

> Анализ фиксирует ценность для пользователя, проектирование - надежную структуру данных

## Кейс «Качели на дереве»: как искажаются требования

Классическая иллюстрация того, что происходит с требованием на пути к коду:

- как **понял заказчик**: качели на дереве
- как **объяснили менеджеру**: подвесное сиденье на ветке
- как **спроектировал аналитик**: площадка, три сиденья, лестница, ГОСТ
- как **сделал программист**: платформа на сваях посреди поля
- что заказчику **было нужно на самом деле**

> Каждый переход «потребность → требование → модель → код» теряет смысл.
> Анализ и проектирование существуют, чтобы эти потери были минимальными

## Цена ошибки на разных этапах

- Ошибка на этапе **требований** — ×1
- **Проектирование** — ×3…×5
- **Кодирование** — ×10
- **Тестирование** — ×20…×50
- После **внедрения** — ×100 и более
- Пример ×100: **Ариан-5 (1996)** — требования не были пере-проверены при повторном использовании кода с Ариан-4: ракета погибла через 37 секунд после старта, потеряно ~$370 млн

> Качественный анализ и проектирование — самая дешёвая «страховка»: на бумаге менять дешевле, чем готовую систему

---

## Цена ошибки: Сбой обновления CrowdStrike Falcon (2024)

- **Этап, где возникла ошибка**: Тестирование и развертывание
- **Что произошло**: Невалидный конфигурационный файл с 21 полем вместо 20 обошел валидатор из-за логической ошибки стенда и вызвал чтение за границами памяти на 8,5 млн хостов Windows
- **Цена**: ~$5,4 млрд потерь компаний Fortune 500, >9 500 отмененных авиарейсов, остановка работы больниц и банковских систем
- **Вывод для моей проектной работы**: Внедрять строгую валидацию входных схем данных, изолированные регрессионные автотесты и поэтапное развертывание в CI/CD

> [CrowdStrike Channel File 291 Incident RCA](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf) · [Parametrix Fortune 500 Report](https://www.parametrixinsurance.com/reports-white-papers/crowdstrikes-impact-on-the-fortune-500)

## Системный анализ: деятельность и артефакты

**Деятельности**:
- выявление потребностей: интервью, анкетирование, наблюдение
- моделирование AS-IS → TO-BE (что улучшаем и как должно работать)
- формулирование и проверка требований с заказчиком

**Артефакты аналитика**:
- глоссарий предметной области
- варианты использования (Use Case), пользовательские истории
- спецификация требований (SRS), прототипы интерфейса

---

## Проектирование ПО: деятельность и артефакты

**Деятельности**:

- архитектурные решения: платформа, фреймворки, хранение данных
- разбиение системы на компоненты и их взаимодействие
- проектирование данных (ER), интерфейсов, алгоритмов

**Артефакты проектировщика**:

- схема архитектуры, диаграммы классов (UML)
- ER-модель и схема БД
- контракты API, макеты пользовательского интерфейса

> Граница: анализ живёт в предметной области, проектирование — в будущей системе

## Жизненный цикл ПО (SDLC)

**Жизненный цикл** — период от возникновения замысла системы до вывода её из эксплуатации.

Типовые этапы:

1. Анализ требований
2. Проектирование (архитектура, детали)
3. Реализация (кодирование)
4. Тестирование и отладка
5. Внедрение и сопровождение

**Стандарты**: ISO/IEC/IEEE 12207 · ГОСТ 34.601-90 · ГОСТ Р 57193-2016

## Каскадная модель (Waterfall)

Анализ требований → Проектирование → Кодирование → Тестирование → Эксплуатация

**Плюсы**: простота планирования, полная документация, предсказуемость.

**Минусы**: результат виден в конце; изменения дороги; высокие риски при неточных требованиях.

- Подходит: стабильные требования, госконтракты, проекты с фиксированным ТЗ (часто — по ГОСТ 34).

## V-модель

- Левое «крыло» V — **декомпозиция**: анализ → архитектура → детальное проектирование
- Правое «крыло» — **верификация** каждого уровня: модульные, интеграционные, системные, приёмочные тесты
- Каждый уровень проектирования связан с уровнем тестирования

**Ключевая идея**: тесты планируются **параллельно** с проектированием, а не после кодирования. Для систем с высокими требованиями к надёжности.

## Спиральная модель (Б. Боэм, 1988)

Проект проходит **несколько витков (итераций)**. Каждый виток:

1. Определение целей и ограничений
2. Анализ рисков, прототипирование
3. Разработка и тестирование версии
4. Планирование следующего витка

**Плюсы**: ранняя работа с рисками, постепенная детализация требований.
**Минусы**: сложное управление, дорогие оценки рисков, нужны опытные аналитики.

## Инкрементная и итерационная модели

**Инкрементная** — система наращивается **частями** (модуль за модулем): после каждого цикла — новый работающий фрагмент продукта.

**Итерационная** — версия уточняется **целиком** от витка к витку: после каждого цикла — более полная и точная версия всего продукта.

- Обе — «мостик» между каскадом и Agile: короткие циклы + накапливаемый результат
- Спиральная модель ≈ итерационная + явный **анализ рисков** на каждом витке

---

## Сравнение моделей ЖЦ

| Модель | Требования | Риски | Первая версия | Тип проекта |
|---|---|---|---|---|
| Каскад | фиксируются в начале | видны поздно | в конце | ТЗ по ГОСТ |
| V-модель | фиксируются | снижены тестами | в конце | надёжные системы |
| Спираль | уточняются на витках | анализ на каждом витке | после 1-го витка | крупные, рискованные |
| Инкрементная | уточняются частично | средние | после 1-го инкремента | развиваемые продукты |
| Scrum | меняются постоянно | снижены спринтами | за 1 спринт | продукты, стартапы |

## Гибкая методология (Agile)

**Агильный манифест (2001)**:

- Люди и взаимодействие — важнее процессов и инструментов
- Работающий продукт — важнее исчерпывающей документации
- Сотрудничество с заказчиком — важнее согласования условий договора
- Готовность к изменениям — важнее следования первоначальному плану

**Итеративно-инкрементная разработка**: продукт наращивается короткими итерациями (1–4 недели), требования уточняются постоянно.

## Scrum: роли и события

**Роли**: Product Owner — приоритизирует бэклог; Scrum Master — снимает препятствия; команда — кросс-функциональная, 3–9 человек.

**Артефакты**: Product Backlog, Sprint Backlog, Инкремент.

**События**: спринт (1–4 нед.), планирование, ежедневный скрам, ревью, ретроспектива.

- Scrum — самая распространённая реализация Agile в индустрии.

---

## RUP (Rational Unified Process)

- Итерационный каркас процесса разработки от Rational/IBM
- **Фазы**: Начало → Уточнение → Построение → Внедрение
- **Дисциплины**: бизнес-моделирование, требования, анализ и проектирование, реализация, тестирование, развёртывание
- Итерации пробегают фазы неоднократно; работы по дисциплинам идут **параллельно** с разной интенсивностью
- Использует UML как основной язык моделирования

## Каскад или Agile: критерии выбора

| Критерий | Каскад | Agile (Scrum) |
|---|---|---|
| Требования | стабильные, известны | меняются, неясны |
| Заказчик | на границах этапов | вовлечён постоянно |
| Регуляторика | ТЗ, ГОСТ, сертификация | гибкие договоры |
| Команда | большая, специализация | малая, универсальная |
| Цена ошибки | высока → усиленный анализ | снижена итерациями |

> На практике часто **гибрид**: каскадная документация + итерационная реализация

## Модель ЖЦ: Финансовый трекер

**Выбранная модель**: Гибридная (Scrum-спринты + каскадные контрольные точки)

**3 аргумента выбора** (по критериям лекции):
1. **Требования**: Пользовательские сценарии уточняются итеративно по итогам тестирования прототипов
2. **Регуляторика и сроки**: Фиксированный семестровый график курса СТРПО требует прохождения строгих контрольных точек и сдачи v1.0.0
3. **Команда**: Малый состав требует быстрой смены задач, регулярных стендапов и 2-недельных спринтов

**Что остается от каскадной дисциплины**:
- Предварительное проектирование ER-модели базы данных и REST API
- Ведение документации и обязательные чек-листы приемки релизов

## Роли в команде разработки

- **Аналитик** — переводит бизнес-потребности в требования и модели
- **Архитектор** — принимает ключевые решения о структуре системы
- **Разработчик** — реализует систему на выбранном стеке
- **Тестировщик (QA)** — проверяет соответствие требованиям
- **DevOps-инженер** — сборка, развёртывание, мониторинг

- В командах проектной работы (3–5 человек) роли **совмещаются**: за год вы попробуете каждую.

---

## Бизнес- и системный аналитик

- Выявляет и формализует требования: интервью, анкетирование, наблюдение
- Строит модели: Use Case, IDEF0, DFD, пользовательские истории
- Ведёт спецификацию требований (SRS), согласовывает её с заказчиком
- Участвует в приёмке: критерии приёмки (acceptance criteria)

**Навыки**: коммуникация, моделирование, знание предметной области, письменная речь.

---

## Архитектор ПО

- Определяет **архитектурные решения**: платформа, фреймворки, хранение данных
- Разбивает систему на модули/компоненты, определяет их взаимодействие
- Следит за качественными атрибутами: производительность, масштабируемость, безопасность, сопровождаемость
- Обеспечивает соответствие архитектуры требованиям и ограничениям

- Архитектор «держит целостность замысла», пока команда реализует части.

---

## Разработчик

- Реализует модули по проектной документации
- Следит за качеством кода: стиль, читаемость, тесты
- Участвует в код-ревью, пишет документацию к коду
- Устраняет дефекты по сообщениям тестировщиков

**Важные качества**: владение языком/стеком, декомпозиция задач, дисциплина версионирования (Git), оценка сроков.

---

## Тестировщик (QA)

- Разрабатывает тест-кейсы на основе требований
- Проводит функциональное и нефункциональное тестирование
- Регистрирует дефекты в баг-трекере, проверяет исправления
- Оценивает готовность продукта к релизу

- Тестировщик даёт команде **раннюю отрицательную обратную связь** — когда исправить ошибку ещё дёшево.

---

## DevOps-инженер

- Выстраивает CI/CD: автоматическая сборка, тестирование, развёртывание
- Управляет инфраструктурой: облака, контейнеры, конфигурации
- Организует мониторинг и логирование работающих систем
- Сокращает путь «код → работающий продукт» с недель до часов

- Инструменты: Git, Docker, CI/CD-серверы, системы мониторинга.

## Матрица RACI

Инструмент распределения ответственности:

| Буква | Смысл |
|---|---|
| **R** — Responsible | Исполнитель: выполняет работу |
| **A** — Accountable | Владеет результатом; **одна** на задачу |
| **C** — Consulted | Консультируемый: даёт экспертизу |
| **I** — Informed | Информируемый: узнаёт о результате |

- Правило: **одна A** на задачу, R может быть несколько.

---

## Пример RACI для проектной работы

| Задача | Тимлид | Команда | QA | Преподаватель |
|---|---|---|---|---|
| Идея и бэклог продукта | R/A | C | C | C |
| Архитектура (ADR) | A | R | C | C |
| Реализация фич | A | R | C | I |
| Тестирование релиза | A | C | R | I |
| Защита релиза v1.0.0 | R | R | R | A |

- В реальных командах матрица строится по функциональным ролям; правило «одна A» заранее снимает спор «кто отвечает».
